### 4.2 共享 Chunk 分解

```
First Load JS shared by all           87.1 kB
  ├ chunks/23-9e356bd0759c31ab.js     31.5 kB    ← React 18 + Next App Router runtime
  ├ chunks/fd9d1056-d73a754fcc98cb13.js  53.6 kB  ← Tailwind classes + lucide-react
  └ other shared chunks (total)         1.96 kB    ← 小 chunk（metadata JSON 等）
```

> **关键结论**：
> 1. 共享 chunk 87.1 kB = 框架 + Tailwind + 图标库，是真正的"首屏不可避免"部分。业务代码占首屏的 Route Size 极小（首页仅 190 B）。
> 2. 公共组件抽象（PageHero / CategoryFilter / EmptyState）都被 Tree-shake 到 shared chunks 或按需 lazy，**未造成单个 FLJS 膨胀**（所有页 FLJS 在 97–112 kB 窄区间内）。
> 3. 6 个前台页的 Banner 之前 6 份重复 DOM 现在合并为 1 份 PageHero 组件，间接降低 gzip 后重复字符串比例（实测 gzip 前 87 kB → 实际网络传输预计 25–30 kB）。

## 5. 后端接口响应性能复测（10 接口 × 5 次连续调用）

**测试方法**（纯 Node `http.request`，Date.now 差分，无额外依赖）：
```js
for (url in urls) for (k=0..4) fetchSync(url); avg = Σms / 5
```
**测试机器**：本地后端 PID 16769（已编译 dist/app.js，HTTP 1.1 keepalive）。

| 接口 | 优化前 avg（基线） | 优化后 avg（实测） | HTTP 状态 | 备注 |
|---|---|---|---|---|
| `GET /api/products` | 1 ms | 2 ms | 200 | 5 产品列表，无 join |
| `GET /api/products?category=智能交通` | 1 ms | 1 ms | 200 | 分类筛选走 Prisma where |
| `GET /api/solutions` | 1 ms | 1 ms | 200 | 4 方案列表 |
| `GET /api/news?page=1&pageSize=5` | 1 ms | 1 ms | 200 | 新闻分页，take 5 skip 0 |
| `GET /api/jobs` | 1 ms | 1 ms | 200 | 6 职位列表 |
| `GET /api/logo/current` | 1 ms | 1 ms | 200 | logoConfig 单条查询 |
| `GET /api/footer` | 1 ms | 1 ms | 200 | footerConfig 单条查询 |
| `GET /api/search?q=AI` | 2 ms | 3 ms | 200 | 全文搜索（产品/方案/新闻 name+description LIKE），相对最贵 |
| **`GET /api/page-configs/home/hero`**（**新增**） | N/A | 1 ms | 200 | 公开 GET，未命中返回 data:null |
| **`GET /api/page-configs/home/values`**（**新增**） | N/A | 1 ms | 200 | 同上 |
| **Overall 平均** | **1 ms** | **1 ms** | 全部 200 | ✅ 无性能退化 |

> **为什么还是 1 ms**：SQLite 在本地是文件读取 + 内存缓存，简单查询的下界就在几百 µs 级别，Prisma 连接池与 `prisma.pageConfig.findUnique` 使用唯一索引 (`@@unique([page,section])`)，是 O(1) 级 BTree 查找；`JSON.parse(content)` 一次性小字符串开销 < 0.05 ms。**接口性能瓶颈不在 DB 查询**（Phase 1 已确认无 N+1），真正瓶颈在广域网 RTT。

### 5.1 生产网络接口耗时估算

| 部署形态 | 单次接口往返（RTT） | 首屏需要的接口数 | 总接口耗时估算 |
|---|---|---|---|
| 同机房 Nginx 反代 → Node（内网） | 0.3 ms | 3–5 | 3–5 ms |
| 用户 → CDN 边缘 → 源站（华东 4G/5G） | 30–60 ms | 3–5 | 90–300 ms |
| 用户 → 海外（北美 4G） | 150–250 ms | 3–5 | 450–1,250 ms |

> **推荐优化（第 2 月）**：在 Next.js 前端对公开 API 启用 `fetch(... , { next: { revalidate: 3600 } })` 或接入 ISR。本次改造首页的 Hero/Values/AboutEntry 三个 fetch 已默认 `revalidate: 3600`，一小时内仅打一次后端，冷启动首屏无需等待接口。

## 6. LCP（最大内容绘制）估算

LCP 是 Google Core Web Vitals 核心指标，取值取决于页面上**最大可见元素**（通常是 Banner 图）的加载时间。对于新蓝恒成官网：

| 页面 | 最大 LCP 元素 | 元素原始大小（WebP，估计） | **3G 网络（750 kbps）LCP 估算** | **4G/WiFi LCP 估算** |
|---|---|---|---|---|
| `/` 首页 | hero_bg.jpg (1920×900) | ~250 kB | 2.7–3.0 s | 0.8–1.1 s |
| `/products`（6 页 Banner 类似） | Unsplash 意境图（1600×1000） | ~200 kB（CDN 自带压缩） | 2.3–2.6 s | 0.7–1.0 s |
| `/products/[slug]`（产品详情） | 产品封面图 (1200×675) | ~120 kB | 1.4–1.7 s | 0.5–0.7 s |
| `/news` 列表 | Banner 意境图 | ~200 kB | 2.3–2.6 s | 0.7–1.0 s |

**分解公式**（以首页 3G 为例）：
```
LCP ≈ DNS(50ms) + TCP+TLS(120ms) + HTML(First Load JS 87kB × 8/750kbps = 0.93s)
     + 图片请求 RTT(150ms) + 图片传输(250kB × 8/750kbps = 2.67s)
     ≈ 3.0 s（估算区间 2.7–3.0s）
```

**第 2 月优化可落地建议**（可立刻下降 40%+，无需改代码逻辑）：

| 优化项 | 预期 LCP 下降 | 实现难度 | 说明 |
|---|---|---|---|
| ① Banner 意境图接入 Next Image `quality=75` AVIF/WebP 自动格式 | ⬇ 30–40% | 低（`next.config` + `<Image>` 默认已支持） | 200 kB → 110 kB AVIF |
| ② Unsplash 图换本地 `/images/` + 七牛/阿里云 Image CDN 自动裁剪 w=900 | ⬇ 10–15% | 低 | 避免 Unsplash 回源延迟 200+ ms |
| ③ 预加载首页 Hero bg：`<link rel="preload" as="image" href="/images/hero_bg.jpg">` | ⬇ 5–10% | 低 | `<Image priority` 默认已做 |
| ④ Shared Chunk 接入 Brotli 预压缩（Nginx gzip_static） | ⬇ 5% | 低 | 87 kB → Brotli ≈ 22 kB |

## 7. 风险评估 + 性能回退策略（逐项）

> 性能类与功能类的风险/回滚分开管理。性能类关注「新版本是否比基线慢」，功能类关注「是否能用」。

| 项目 | 风险点 | 概率 | 影响 | 监控手段 | 回滚命令 |
|---|---|---|---|---|---|
| **Build 包体** | 未来新增 Banner/Filter 不复用公共组件导致 FLJS 增长 | 中 | 单页 First Load 超 120 kB（目前 97–112） | CI `next build` 输出表格保存到 artifact，每次 diff | 任何 PR 引入重复 Banner，git revert 即可 |
| **PageConfig 路由** | 管理员频繁改首页配置导致 revalidate 3600s 不生效，前端展示旧内容 | 低 | 旧文案展示 1 小时，用户反馈后台"保存不生效" | 管理后台「立即刷新首页缓存」按钮（下一阶段）：`fetch('/api/revalidate', { method: 'POST' })` |
| **SQLite 写入** | Messages / Applications 用户真实提交量大时，SQLite 单连接写排队 | 极低（QPS 估计 < 1） | 写入延迟从 5 ms → 50 ms | 日志 `logger.info` 中记录写入耗时 | 迁移到 Postgres（Prisma 只改 DATABASE_URL + 一条 migrate，代码零改动） |
| **首页 SSR** | Hero props fetch 异常时走本地 seed JSON（兜底正常），但日志无告警 | 低 | 首页永远"看起来正常"，但实际后端挂了无人知 | 下一阶段接入 Sentry：`getHeroData` catch 时 `Sentry.captureException(err)` | N/A（无需回滚，是增强） |
| **全局**（性能整体回退） | 某次迭代后 LCP 从 3s → 5s | 中（常见） | Core Web Vitals 评分下降 → SEO 排名下降 | 每次上线前跑一次 Lighthouse 移动端模式 + 本报告基线作 diff | `git reset --hard <last-good-commit>`，或发布蓝绿时切回旧容器镜像 |
